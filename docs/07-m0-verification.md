## 1. 这份手册解决什么

当前 `docs/02` 里有 13 项标注为「待实测」的假设，它们卡着这些设计：

| 假设 | 一旦不成立要改的地方 |
| --- | --- |
| Worker 能创建、能装载同目录多文件 | [ADR-0001](./adr/0001-worker-code-packaging.md) 的方案选择（方案 A → 方案 B 打包） |
| `format: 'PCM'` + `frameSize` 分帧连续 | 录音管线（`core/audio/record.ts`）与 [03 §3](./03-audio-engine.md#3-素材导入管线) |
| 解码长音频不会 OOM | 导入时长上限与内存预算（[06 §4](./06-engineering-roadmap.md#4-性能与内存预算)） |
| Canvas 2D 能跑到 30fps | 波形画布的重绘策略（[06 §4.1](./06-engineering-roadmap.md#41-豁免登记) 的豁免项） |

跑完一轮的目标：**把上表每一行变成"已结论"**，或者明确知道要改哪里。

## 2. 三条上机路径（选一条）

| 路径 | 需要什么 | 说明 |
| --- | --- | --- |
| **A. 体验版（推荐）** | 个人主体小程序号（手机可注册） | **不需要第二块屏幕**：上传后在微信里直接打开体验版 |
| B. 预览二维码 | 第二块屏幕（或另一台设备） | 微信预览码**只能摄像头扫**，不能从相册识别 |
| C. PC 微信开发者工具 | 一台 PC | 可直连真机调试；测试号即可 |

### 路径 A：体验版（无需扫码）

```bash
# ① 注册个人主体小程序号（手机浏览器，10~15 分钟）
#    https://mp.weixin.qq.com/ → 立即注册 → 小程序 → 邮箱激活 → 主体信息（身份证 + 本人微信扫码）
# ② 拿到 AppID 后，在 mp 后台生成上传密钥：
#    开发管理 → 开发设置 → 小程序代码上传 → 生成密钥 → 下载 private.<appid>.key
# ③ 手机上传密钥文件到 Termux（下载目录 → 项目根）
termux-setup-storage                       # 首次需要（授权存储）
cp /sdcard/Download/private.wx*.key .
cp mp.config.example.json mp.config.json   # 填入 appid 与密钥文件名
npm run mp:doctor                          # 自检：凭据、目录、必填文件（不打印私钥）
npm run mp:upload                          # 上传（miniprogram-ci，无需扫码）
# ④ 打开：微信 → 发现 → 小程序 → 搜索自己的小程序名 → 进去就是刚上传的版本
```

上传成功后 `mp:upload` 会打印版本号，并提示到 mp 后台「版本管理」里把该版本设为体验版
（手机浏览器可操作）。**开发版本**本身也能被开发者自己打开，够 M0 用。

> 如果卡在②（找不到密钥入口）：说明该账号类型不提供上传密钥。测试号常见如此 —— 那种情况下只能走路径 B/C。

### 路径 B：预览二维码

```bash
cp mp.config.example.json mp.config.json   # 填 appid 与密钥路径
npm run mp:doctor
npm run mp:preview                         # 生成 mp-qrcode.png（默认打开 spikes 页）
# 脚本会自动复制到 /sdcard/Pictures，并提示三种打开方式
```

微信扫一扫**只能扫屏幕上的二维码**；从相册识别图片对预览码无效（平台限制，见 [02 §5](./02-platform-capability.md#5-待实测验证清单spike-任务)）。

## 4. 上机顺序

`spikes/index/index` 里的实验已按"便宜的、不需要人工操作的"排在前面，建议顺序执行；不需要一次跑完，结果可以分批复制。

| 批次 | 实验 | 为什么这个顺序 |
| --- | --- | --- |
| ① 架构前提 | DB-05、DB-06 | Worker 能不能用决定渲染架构；不成立时后面的性能实验没有意义 |
| ② 文件与存储 | DB-07、DB-03、DB-02、DB-10、DB-14 | 只读/写临时文件，互不干扰 |
| ③ 音频能力 | DB-01、DB-04、DB-09、DB-13 | DB-01 需要你从聊天记录里挑文件 |
| ④ 需要人工配合 | DB-08、DB-11 | 录音 15 秒；分享面板会真的弹出来 |

> DB-12（纯 JS 性能）已在 Node 侧跑完并回填 [06 §4](./06-engineering-roadmap.md#4-性能与内存预算)，真机复测可留到有设备时补做。

## 5. 逐项操作

每项都点「运行」，跑完点「复制全部结果」把文本存下来。**通过标准的定义在 [02 §5](./02-platform-capability.md#5-待实测验证清单spike-任务)**，下表只写"你要做什么、看哪几行"。

| 编号 | 你要做什么 | 重点看哪几行 | 通过线（详见 02 §5） |
| --- | --- | --- | --- |
| DB-05 | 直接运行（不需要操作） | Worker 内可用内建对象清单、多文件装载、`useExperimentalWorker` | 得到确定的代码组织形式（对应 ADR-0001 方案 A/B） |
| DB-06 | 直接运行 | 1MB/10MB 往返耗时、transferable 是否生效 | 得出单块最优大小 |
| DB-07 | 直接运行（会自建 30s 素材） | 4KB / 64KB / 1MB 三种块的 MB/s 与"最优块大小" | ≥ 20MB/s |
| DB-03 | 直接运行 | `getChannelData` 耗时、`copyFromChannel` 是否可用 | 明确导入管线取 PCM 的写法 |
| DB-02 | 直接运行（逐级 1/2/3/5/8 分钟） | 每级 OK/FAIL 与耗时 | 得到可安全解码的最大时长（立体声等价时长减半） |
| DB-10 | 直接运行 | 10/50/90/100/110/150/210MB 哪一级先失败、是否出现 `1300202` | 确认 100MB 上限 |
| DB-14 | 直接运行（会写到接近配额，结束自动清理） | 累计可写 MB、失败信息 | 是否与 200MB 吻合 |
| DB-01 | 运行时**从聊天记录里选音频**（mp3/m4a/wav/amr 各一个最好） | 每个扩展名的 OK/FAIL | 得到支持矩阵 |
| DB-04 | 直接运行（等待 1 秒） | `createScriptProcessor` 是否存在、1 秒内回调次数 | 得出可行性结论（当前设计不依赖它） |
| DB-09 | 直接运行（会外放 12 秒标记音，可听每秒一个短音） | `duration`、seek 误差、推进量、`playbackRate` 写入 | seek 误差 < 100ms |
| DB-13 | 直接运行 | 平均/P95 单帧耗时、等效帧率、10 万条竖线耗时 | 单帧 ≤ 33ms（30fps） |
| DB-08 | 点运行后**对着麦克风持续说话 15 秒**（中途别切后台） | 分帧数、帧大小种类、最大帧间隔、时长误差 | 帧大小恒定、时长误差 < 50ms |
| DB-11 | 点运行后会弹分享面板，**发送给朋友或取消都算通过** | 分享结果一行 | 能唤起面板 |

**容易踩的坑**

- DB-08 第一次会弹麦克风授权，拒绝后需去设置里开启（实验页会提示）。
- DB-14 会占用接近 200MB，跑完自动清理；若中途退出小程序，残留文件在 `USER_DATA_PATH/spikes/` 下，重跑或删除工程即可释放。
- DB-11 若一直失败并提示 `cancel`，说明面板已弹出（脚本按"可用"处理）。
- DB-09 的 `duration` 应接近 12.000s；若明显不符，说明自产 WAV 的头部写法有问题（那会推翻 [03 §2](./03-audio-engine.md#2-中间格式规范)）。
